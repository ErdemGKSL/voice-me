- (decision by user) AD: Design paradigm is Hexagonal / Ports-and-Adapters. voice-me-core defines platform-agnostic domain types and trait 'ports' (HotkeyBackend, VirtualMicBackend, TtsSidecarClient, etc.); per-OS implementations (Linux/Windows) and the gpui-kit UI are adapters plugged into those ports. Rationale: OS-specific hotkey/audio code already needs per-platform variation (PRD-driven); ports-and-adapters lets Linux-first development add a Windows adapter later without touching the core, and lets the IPC mechanism to the Python sidecar change without touching UI or hotkey code.
- (decision by user) AD: Per-OS adapter code lives in fully separate crates per OS (e.g. voice-me-hotkey-linux, voice-me-hotkey-windows; voice-me-audio-linux, voice-me-audio-windows), each implementing the shared port trait from voice-me-core. voice-me-app picks the right crate at compile time. Chosen over cfg(target_os) branching within one crate: matches the 'split aggressively into crates' direction and means building/testing one platform never pulls the other platform's dependencies.
- (decision by user) AD: voice-me-core owns a single AppState (settings: hotkey binding, active Reference Voice Sample, UI language, selected virtual mic device). No adapter (UI, hotkey, audio, tts) mutates AppState directly - all mutation goes through core use-case functions. All adapters signal into the app through one shared AppEvent channel/type (e.g. hotkey pressed, sidecar generation done, dependency check result) rather than each inventing its own callback/polling mechanism. GPUI/gpui-kit UI listens to this channel via cx.spawn and updates its Entity accordingly. Prevents: divergent per-adapter state copies and inconsistent event-delivery mechanisms that would need separate integration work later.
- (decision by user) AD: Error handling - voice-me-core defines a thiserror-based domain error enum; each adapter maps its own errors (IPC failure, driver failure, IO failure) into it at the port boundary; voice-me-app aggregates with anyhow at the composition root. No adapter-specific error type crosses into another crate or the UI.
- (decision by user) AD: Async runtime - run Tokio alongside GPUI's own executor (not GPUI's executor alone). Adapters needing async I/O (voice-me-tts sidecar IPC, voice-me-deps HTTP downloads) run on Tokio; results cross into the GPUI/AppEvent world via the shared AppEvent channel from AD (state ownership). GPUI's own cx.spawn/background_spawn stays for UI-side async work only. Prevents each adapter picking a different or no async runtime.
- (decision by user) AD: Settings persistence - single TOML file at the OS-appropriate config dir (via the 'directories' crate: XDG on Linux, AppData on Windows), holding hotkey binding, active Reference Voice Sample path, UI language, selected virtual mic device. Only voice-me-core reads/writes it, behind a SettingsStore port; adapters never touch the file directly.
- (convention by user) Logging - 'tracing' crate, initialized once centrally in voice-me-app; no crate sets up its own logger or invents its own log-level scheme.
- (version) GPUI: pre-1.0, crates.io 0.2.2 is stale/misleading - depend via git on github.com/zed-industries/zed pinned to a specific rev/tag, not crates.io semver
- (version) gpui-kit: crates.io, latest 0.6.4, pins its own compatible GPUI revision internally - app depends on gpui-kit only, not GPUI directly
