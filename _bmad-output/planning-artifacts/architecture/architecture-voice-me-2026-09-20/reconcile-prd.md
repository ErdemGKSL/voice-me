# Reconciliation: PRD → Architecture Spine

The spine is intentionally minimal (paradigm, crate-direction rules, state ownership, error handling, async runtime, settings, CI/release) and mostly succeeds at not restating PRD features. Cross-checking all 9 FRs, the Open Questions, and the NOTE FOR PM callouts against it surfaces a handful of real gaps — places where the PRD implies a durable invariant or a cross-cutting risk that a future builder reading only the spine would miss, plus one place where the spine actually under-treats a risk the PRD called foundational.

## Gaps

- **GPUI tray/global-hotkey feasibility risk (Open Question 6, both NOTE FOR PM callouts in §4.2/§4.5) is not carried into the spine's Deferred section or ADs, despite the PRD calling it "a foundational feasibility question for the whole UI shell, not a detail."** The spine's crate diagram just asserts `voice-me-hotkey-linux`/`-windows` crates implement `HotkeyPort`, as if the underlying capture mechanism (hand-rolled per-OS shim vs. depending on the unverified "Adabraka GPUI" fork vs. a separate crate like `global-hotkey`) is a solved detail. Deferred only lists "Anti-cheat compatibility of the chosen hotkey-capture approach" — it never mentions that a *hotkey-capture approach doesn't yet exist to choose from*, or that GPUI itself may not be the vehicle for it. Fix: add a Deferred/Open-Risk entry stating that `HotkeyPort`/tray implementations may need to bypass GPUI's window/app-lifecycle machinery entirely (e.g. a bare OS-level hook running outside `cx.spawn`), and that this could require restructuring `voice-me-app`'s composition root once resolved.

- **System tray (FR-2) gets no architectural treatment at all, unlike hotkey and virtual-mic — an inconsistency given all three share the same GPUI-gap risk.** AD-2 ("per-OS adapters are separate crates") explicitly binds FR-3 (hotkey) and FR-6 (virtual mic) but not FR-2 (tray), and the Structural Seed has no `voice-me-tray-*` crate or `TrayPort` trait — tray just lives inside `voice-me-app`/`voice-me-ui` per the Capability Map. If tray turns out to need its own per-OS native shim (as the PRD flags is plausible), there's no port/crate boundary reserved for it, and it would leak into the composition root or the UI crate against AD-1's own spirit. Fix: either extend AD-2 to explicitly bind FR-2 and reserve a `TrayPort` + per-OS tray crates in the Structural Seed, or add an explicit Deferred note explaining why tray was scoped differently from hotkey/mic.

- **No storage/ownership rule for the Reference Voice Sample audio file itself (FR-1).** AD-6 pins down *settings* (one TOML file, owned by core) but the PRD's FR-1 consequences require a saved, re-recordable audio asset — a different kind of local state with its own directory, format, and lifecycle (replace/delete on re-record). Nothing in the spine says who owns that file's location or how `voice-me-core`/`SettingsStore` reference it (path in TOML? content-addressed blob dir?). This is exactly the kind of "state ownership" invariant the spine's own stated purpose calls out, and it's silent. Fix: extend AD-6 (or add AD-6a) to state that binary user assets (Reference Voice Sample, and later any cached model/dependency downloads) live under a `directories`-resolved data dir, referenced by path from the TOML, never duplicated into settings.

- **No invariant on network egress / "local-only, no telemetry" (PRD Non-Goals §5, Vision §1) even though AD-7 already gestures at it for one crate.** AD-7 restricts *`voice-me-deps`'* remote fetches to this repo's GitHub Releases, but the PRD's stronger claim — "no cloud calls... no telemetry beyond what stays on-device" — is a whole-app constraint, not just a dependency-provisioning one. As written, nothing stops a future contributor from adding, say, a crash-reporting call in `voice-me-app` or a phone-home in `voice-me-tts`, without violating any stated rule. Fix: add a short AD (or fold into AD-7) stating network access is restricted to `voice-me-deps`→GitHub Releases; every other crate, including `voice-me-tts`'s sidecar IPC, is local-only (loopback/stdio), and this is a violation-checkable rule, not just a vision statement.

- **No mechanism for GPU-availability / CPU-fallback (FR-7's "Chatterbox-Nano" degradation) to actually reach `voice-me-tts`.** `voice-me-deps` owns dependency/GPU detection (AD-7's domain) and `voice-me-tts` owns the TTS engine invocation, but the spine never says how the detection result crosses that boundary — through `AppState` (per AD-3's "no adapter mutates it directly... only through voice-me-core use-case functions"), or a dedicated field/port. Without this, an implementer could easily wire `voice-me-deps` and `voice-me-tts` together directly, which AD-1 forbids for adapter-to-adapter coupling. Fix: one line under AD-3 or the Capability Map: GPU/model-variant state is part of `AppState`, written by `voice-me-deps` via a core use case and read by `voice-me-tts` the same way.

- **Sidecar Process lifecycle/supervision (start timing, crash/restart policy) isn't addressed**, even though AD-5 covers the async-runtime bridge for talking to it. FR-5's "Sidecar Process unavailable" failure case implies some supervision policy (lazy-start on first Speak Action vs. eager-start at app launch; auto-restart on crash vs. surfacing an error) that affects both perceived latency (SM-2) and the "clear failure indication" requirement. This is arguably too implementation-level for the spine, but at minimum it's absent from Deferred, so a future builder won't know it was consciously left open. Fix: add a one-line Deferred entry: "Sidecar Process start/crash-supervision policy — affects first-Speak-Action latency and FR-5's failure UX; not decided here."

- **The "Overlay closes before TTS completes" sequencing guarantee (FR-4) isn't stated as an invariant**, only implied by AD-3's general AppEvent pattern. This is the one piece of latency-feel/UX intent (Prompt Overlay must never block on generation) that has real architectural teeth — get it wrong and the whole "type, Enter, gone" interaction breaks — yet it reads only as a UI behavior note in the PRD, not as a rule binding `voice-me-ui`/`voice-me-tts` interaction. Fix: add a short rule under AD-3 or AD-5: dismissing the Prompt Overlay is synchronous and never awaits the `TtsPort` call; the Speak Action is fire-and-forget from the UI's perspective, with completion/failure delivered later via `AppEvent`.

No contradictions were found between the spine and the addendum's crate-structure proposal or driver research — the spine's per-OS crate split (AD-2) is a permitted refinement the addendum explicitly invited ("to be refined at bmad-architecture, not locked here"), and the Windows driver's unresolved named-pipe control mechanism (Open Question 2) is correctly carried into Deferred.
