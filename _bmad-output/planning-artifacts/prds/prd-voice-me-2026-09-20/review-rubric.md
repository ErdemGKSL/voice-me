# PRD Quality Review — prd-voice-me-2026-09-20

## Overall verdict
This is a well-calibrated hobby-project PRD: it names its real feasibility risks instead of hiding them (GPUI's missing tray/hotkey support, anti-cheat conflicts, an unconfirmed Windows driver control mechanism), keeps scope honest with explicit Non-Goals and an Assumptions Index, and doesn't over-formalize a single-user tool with persona/UJ padding. The main weaknesses are mechanical rather than substantive: the FR-2a/FR-2 numbering breaks the ID sequence in a way that makes "FR-2 through FR-5" range references in MVP Scope and SM-1 ambiguous about whether FR-2a is included, and a couple of NFR thresholds are punted to implementation without a fallback plan if the numbers come back bad.

## Decision-readiness — strong
The PRD states real, unresolved risks as risks rather than smoothing them over. §4.2's `[NOTE FOR PM]` on GPUI ("GPUI has no built-in system tray or global hotkey support upstream (pre-1.0); a community fork ... is unverified. This is a real feasibility risk for FR-2a and FR-2") is exactly the kind of tension the rubric wants surfaced, not buried. The anti-cheat note on FR-2 ("Global input hooking can trigger anti-cheat systems ... this is a real compatibility risk for the stated 'works during games' goal") is a genuine trade-off acknowledgment, not a rhetorical aside — the PRD is willing to say "we don't know if the core interaction is even safe to ship as designed" without resolving it artificially.

Open Questions (§8) are genuinely open — none carry a buried answer in the next sentence. OQ6 ("Can GPUI ... actually deliver FR-2 and FR-2a directly ... This is a foundational feasibility question for the whole UI shell, not a detail") is stated with appropriate weight rather than downgraded to a footnote.

### Findings
- **low** NFR-with-no-fallback (§4.2 FR-4, §8 OQ1) — Latency is called out as unmeasured with "no hard numeric target is set yet," but there's no stated fallback or de-scope path if measured latency turns out to be unusable for live voice chat (e.g., what happens to the product thesis if Chatterbox-Multilingual V3 can't hit conversational latency on CPU). *Fix:* add one sentence naming the fallback (e.g., "if GPU-required latency is the only viable path, CPU-only becomes a defined non-goal rather than a silently degraded mode").

## Substance over theater — strong
No persona theater: there is exactly one user (the builder), stated plainly in §2 rather than padded into multiple synthetic personas. No innovation/differentiation section was forced in — the PRD explicitly defers competitive framing to `brief.md` (§0) rather than re-manufacturing it here. The Vision statement (§1) is specific to this product's actual mechanism ("a global hotkey pops a tiny prompt... a moment later, the line plays through a virtual microphone in your own voice") — it could not swap into another PRD unchanged. NFRs are assumption-tagged rather than boilerplate; no instances of "must be scalable/secure/reliable" found. No findings.

## Strategic coherence — strong
The thesis is explicit and consistent: situational muteness (§2.1 JTBD) → discrete typed-line playback in the user's own cloned voice, with speed prioritized over fidelity. Feature prioritization follows this — the core loop (FR-2 through FR-5) is the spine, Dependency Management and Localization are supporting, and Preset Phrase (a plausible "easy win" feature) is explicitly deferred to v2 (§5) rather than pulled forward. SM-1 measures actual behavior change ("uses voice-me during real gaming sessions instead of falling back to text chat... at least weekly"), not an activity vanity metric. SM-C1 names the counter-pressure explicitly ("Do not chase maximum voice-clone fidelity... at the expense of end-to-end latency") — this is a real trade-off statement, not a template placeholder.

### Findings
- **low** Implementation detail embedded in MVP Scope (§6.1) — "Rust workspace structured as multiple crates (binary, lib(s), tests) — see `addendum.md` for the proposed breakdown" sits inside the capability-level MVP Scope list, mixed in with feature-level scope items (Voice Setup, Dependency Check, etc.). This is architecture, not product scope, and blurs the PRD/addendum boundary the document otherwise maintains carefully (§0: "Codebase/crate structure... live in this run's own `addendum.md`, not here"). *Fix:* drop this line from §6.1 or move it to a "supporting technical decisions" aside, since the PRD's own stated boundary (§0) says crate structure doesn't belong here.

## Done-ness clarity — strong
Every FR has testable consequences, and — notably — where a numeric bound isn't known yet, the PRD tags it `[ASSUMPTION]` rather than hiding vagueness inside adjectives. FR-3's "without a perceptible delay" is immediately followed by a concrete assumed number ("target under 200ms... no measured baseline yet"), which is the right pattern: readable intent plus an honest placeholder. FR-6 similarly ties "reduced/CPU-only mode" to a named concrete artifact (the "Chatterbox-Nano" variant) rather than leaving it abstract. No unflagged instances of "handles X gracefully" or "user-friendly" were found — the one soft phrase, FR-1's "clear in-app message," is paired with a testable consequence about *when* it must appear (on violating length/format bounds), so it's acceptable.

## Scope honesty — strong
§5 Non-Goals is substantive and specific (platform exclusion, monetization exclusion, feature deferral all named with reasons), not a boilerplate list. The Assumptions Index (§9) is complete and every entry traces to an inline `[ASSUMPTION]` tag in the body (verified: FR-1, FR-3, FR-4, FR-6, FR-7, FR-2a all appear both inline and in the index — see Mechanical notes for one near-miss). Open-items density (6 Open Questions + 7 inline `[ASSUMPTION]` tags + 3 `[NOTE FOR PM]` callouts) is appropriate for a pre-architecture hobby PRD that explicitly isn't a green-light-to-build document — these are risks intended to be resolved at the next stage (`bmad-architecture`), not items silently left for an engineer to discover mid-build. No findings.

## Downstream usability — adequate
This PRD does feed a downstream architecture stage (addendum explicitly says crate boundaries are "to be refined at `bmad-architecture`, not locked here"), so traceability matters here more than for a fully standalone PRD. The Glossary (§3) is used consistently — "Reference Voice Sample," "Prompt Overlay," "Speak Action," "Sidecar Process," "Virtual Microphone," and "Dependency Check" all appear with identical casing everywhere they're used in §4. The single UJ protagonist (Erdem) is named and carries context inline in both UJ-1 and UJ-2.

### Findings
- **medium** FR-2a breaks ID contiguity and makes range references ambiguous (§4.2, §6.1, §7) — FR-2a is introduced *before* FR-2 in reading order ("FR-2a: Run quietly in the background" precedes "FR-2: Configure a global hotkey"), so the sequence in the document is FR-1, FR-2a, FR-2, FR-3... Downstream, §6.1 MVP Scope says "Global hotkey configuration and Prompt Overlay speak flow (FR-2 through FR-5)" and §7 SM-1 says "Validates FR-2 through FR-5" — a reader or a story-generation tool doing naive range expansion (FR-2, FR-3, FR-4, FR-5) would silently drop FR-2a even though it's clearly meant to be in MVP scope (it's the tray/background-process behavior, load-bearing for the whole interaction model). *Fix:* either renumber so FR-2a becomes FR-1a (between Voice Setup and hotkey features) or FR-2's siblings are relettered contiguously, or explicitly write "FR-2a and FR-2 through FR-5" wherever the range is used.

## Shape fit — strong
This is correctly shaped as a lightweight, single-operator hobby spec: one UJ protagonist, one persona, no B2B stakeholder matrix, no forced differentiation/competitive-landscape section (deferred to `brief.md`), and §7 explicitly self-labels as "Hobby-scale — kept intentionally light." It is not over-formalized (no UJ density inflation, no persona theater) and not under-formalized either — the two UJs it does have are load-bearing (UJ-1 anchors FR-2 through FR-5's latency requirement; UJ-2 anchors FR-1 and FR-6). Constraint traceability for the real engineering risks (GPUI gaps, anti-cheat, driver control) is handled through `[NOTE FOR PM]` and Open Questions rather than forced into a compliance-style traceability matrix that wouldn't fit a hobby project. No findings.
